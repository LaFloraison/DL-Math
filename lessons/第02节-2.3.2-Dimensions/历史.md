# 历史：当"几行几列"变成一种语言——形状的力量

## 19 世纪的记法之争：行在前还是列在前？

矩阵理论建立之初，有一个看似琐碎、实则根本的问题：**一个矩阵，该先写行数还是先写列数？**

早期作者各写各的。有的写 $m\times n$（行×列），有的写 $n\times m$（列×行）。凯莱自己在不同论文里也摇摆过。行列式理论里，人们长期只说"一个 $n$ 阶行列式"（方阵，行=列，不用区分）。直到矩阵成为普遍工具，"行数在前"才渐渐成为主流——因为"行"总是人们"先看到"的方向（文字从左到右、从上到下读）。

这场"记法之争"看起来无足轻重，却决定了此后一百多年所有矩阵文献的排版、所有线性代数教材的约定。**一个约定，成了整个世界共享的语法。** 今天 NumPy 里 `A.shape` 返回 `(行数, 列数)`，就是这个约定在代码里的最终形态。

## 计算机时代：形状从"记法"变成"内存的布局"

20 世纪中叶，计算机开始处理矩阵。这时"行在前列在后"不再只是纸面约定——它直接决定了**数据在内存里怎么排**。

按行优先（row-major）存储：先存第 0 行、再存第 1 行……；按列优先（column-major）：先存第 0 列。Fortran 用列优先，C 用行优先，NumPy 默认行优先但两种都支持。**同一个矩阵，两种存储方式，`flatten()` 的结果完全不同**（§2.2.3.1 的习题就踩过这个坑）。

于是"维度"从数学概念长出了工程血肉：它不仅是"几行几列"，还是"内存如何布局、计算如何对齐、GPU 如何并行"。**一个 `shape`，同时是数学的身份和机器的地图。**

## GPU 时代：形状决定速度

当矩阵乘法的吞吐量成为深度学习的命脉，形状又多了一层意义：**性能。**

GPU 把矩阵分块并行计算；矩阵的形状（行数、列数）决定了如何分块、缓存如何复用。同样一个矩阵，`(512, 512)` 的排布可能比 `(512, 513)` 快——因为对齐了 GPU 的分块尺寸。框架（PyTorch）为此做了一件事：很多形状**自动调整**（如把 $n$ 维输入压平到 2 维再算），而 `reshape`、`view`、`contiguous` 这些 API 的存在，正是为了在"形状语义"和"内存布局"之间架桥。

**一个 19 世纪的记法约定，在 21 世纪变成了性能的开关。** 没人预料到"先写行还是先写列"会以这种方式影响世界。

## 留一扇门

从凯莱时代的排版之争，到 GPU 的分块对齐，"形状"走过了一条从"纸面约定"到"性能命脉"的路。

而下一章（§2.4）会把形状推向更高维：当数据变成张量，行和列只是前两个轴，"通道""序列""批次"等更多轴依次登场。你即将掌握的那套"形状语言"，会一路用到 Transformer 的 `(B, T, d)` 和 CNN 的 `(B, C, H, W)`。
